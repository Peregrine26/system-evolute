# CrossDesk 项目总览与需求分析

> 面向三人程序设计课程小组的共同说明。本文描述项目目标与预期交付；除“当前进度”一节外，功能均为计划，尚不代表已经实现。

## 1. 项目定位

CrossDesk 是一个使用 C++、Qt 和 CMake 开发的跨平台桌面窗口管理工具。它借鉴 macOS Mission Control 的交互方式，让用户查看当前窗口、把窗口分配到不同 Workspace，并通过总览界面和快捷键切换工作上下文。目标平台是 Windows 和 Linux X11；Wayland 留作后续研究。

本项目管理的是用户已打开的应用窗口。第一版不替换操作系统的桌面环境或窗口管理器，也不要求其他应用接入 CrossDesk。

课程项目的两个同等目标是：交付可演示的软件；让每位组员能够解释自己负责的桌面系统 API、模块边界和测试方法。我们按“原理 -> API -> 最小可运行示例 -> 编译与测试 -> 合入正式模块”的节奏开发。

## 2. 用户、场景与价值

目标用户是经常同时打开多个应用、需要按任务整理窗口的 Windows/Linux 桌面用户。

典型场景：用户正在写报告，同时开着编辑器、浏览器和聊天软件；将前两者放在“学习” Workspace，把聊天窗口放在“沟通” Workspace；按快捷键打开总览，查看各组窗口，并切换到需要的工作环境。

CrossDesk 应减少寻找窗口和手工摆放窗口的时间，同时让用户始终知道窗口去了哪里、如何找回来。

## 3. 范围与边界

### 第一版目标

- 在 Windows 和 Linux X11 上扫描可管理的顶层窗口，显示标题、应用标识及位置等信息。
- 创建、命名、删除和切换多个 Workspace，并移动窗口的归属。
- 在总览中查看各 Workspace 的窗口，并选择窗口进行定位或切换。
- 对受支持的窗口执行显示/隐藏、移动、调整大小及预设布局。
- 提供常用快捷键和本地配置保存。
- 用 Qt 提供简洁、统一的 Mac-like 交互，但不要求复刻 macOS 的所有动画和视觉细节。

### 暂不纳入第一版

- Wayland 后端、替换系统窗口管理器、跨机器同步、云账号、复杂脚本/插件系统。
- 保证能控制系统窗口、受保护窗口、其他权限级别的窗口或所有特殊应用窗口。
- 将窗口真正迁移到操作系统原生虚拟桌面；此能力须单独评估，不作为默认承诺。

## 4. 功能需求

优先级：P0 为课程演示必须完成；P1 为基础功能稳定后加入；P2 为扩展。

| 编号 | 优先级 | 需求 | 可验收的结果 |
| --- | --- | --- | --- |
| FR-01 | P0 | 扫描当前桌面的顶层窗口 | 能列出窗口标识、标题、所属进程、位置和大小；单个字段获取失败不终止整次扫描。 |
| FR-02 | P0 | 识别适合显示在总览中的窗口 | 无标题、工具窗口或已消失窗口按明确规则处理；规则可测试，且不误删普通应用窗口。 |
| FR-03 | P0 | 管理多个 Workspace | 用户可新建、重命名、删除和切换 Workspace；至少保留一个 Workspace。 |
| FR-04 | P0 | 管理窗口归属 | 用户能把一个窗口移到指定 Workspace；总览能立即反映新的归属。 |
| FR-05 | P0 | 打开窗口总览 | 总览按 Workspace 展示窗口，用户可选择一个窗口并回到对应工作上下文。 |
| FR-06 | P0 | 控制窗口 | 对普通应用窗口执行显示/隐藏、移动和调整大小；失败时给出可理解的反馈。 |
| FR-07 | P0 | Windows + Linux X11 | 两个平台通过同一上层接口完成主要流程；平台差异由后端处理。 |
| FR-08 | P1 | 自动布局 | 至少提供一种可重复的平铺布局，并避免把窗口放到屏幕可用区域之外。 |
| FR-09 | P1 | 快捷键 | 能用快捷键打开总览、切换 Workspace；冲突或注册失败时有反馈。 |
| FR-10 | P1 | 配置保存 | 重启后可恢复 Workspace 名称、窗口分配策略及用户设置；已不存在的窗口安全忽略。 |
| FR-11 | P2 | 窗口缩略图与动画 | 平台允许时显示预览；不可用时回退到标题、应用名称或图标。 |

### 核心交互的异常路径

- 扫描期间窗口可能关闭：跳过失效窗口，不让应用崩溃。
- 查询进程信息可能失败：保留窗口记录，显示“未知应用”等回退信息。
- 移动、隐藏或缩放可能被系统或目标应用拒绝：保留原状态并向用户提示失败。
- 外部应用会自行创建、关闭或移动窗口：下一次刷新应与实际桌面状态同步。

## 5. 非功能需求

| 编号 | 要求 | 验证方式 |
| --- | --- | --- |
| NFR-01 可移植性 | Workspace 和 UI 代码不包含 Win32/X11 类型或头文件；平台调用集中在对应后端。 | 代码审查、两平台分别编译。 |
| NFR-02 稳定性 | 普通窗口关闭、标题为空、权限不足或平台 API 失败时，CrossDesk 不崩溃。 | 人工场景测试和边界测试。 |
| NFR-03 响应性 | 扫描和布局操作不应让总览长时间无响应；以约 50 个窗口的场景检查交互体验。 | 两平台演示机上的人工计时和观察。 |
| NFR-04 可测试性 | Workspace、窗口筛选和布局逻辑可用模拟适配器测试，不依赖真实桌面。 | 自动化单元测试。 |
| NFR-05 可构建性 | 使用 CMake 构建；仓库记录依赖版本、构建命令和两平台测试步骤。 | 组员在另一台开发机按文档构建。 |
| NFR-06 可用性 | 总览能区分当前 Workspace、窗口归属、选中状态和操作失败；关键流程可由键盘完成。 | 组员按验收场景操作。 |

## 6. 架构与依赖方向

```text
Qt UI：总览、交互、状态反馈
        |
Workspace Manager：归属、切换、布局和配置策略
        |
统一 Window API / Window Manager 接口：窗口数据与可用操作
       / \
Win32 Backend   X11 Backend
```

- **Qt UI** 只调用上层服务，不直接操作 `HWND` 或 X11 `Window`。
- **Workspace Manager** 保存业务状态，调用统一接口完成实际窗口操作；其测试使用模拟后端。
- **平台适配器** 把 Win32/X11 的窗口标识、查询结果和错误转换为上层可理解的数据。
- **窗口标识不是永久 ID**：窗口关闭后可失效，配置保存需要另行设计“重新识别窗口”的策略。

当前仓库已有 `WindowInfo`、`WindowApiAdapter`、`Win32ApiAdapter` 和 Windows 扫描器。接口目前只支持查询；窗口控制、错误表达和 X11 实现要在后续阶段通过小实例逐步加入。已有扫描器的名字带有 `Windows`，将来引入通用扫描流程时再调整，不应把这个名字视为最终跨平台接口。

## 7. 三人分工与协作接口

采用一位主负责人、两位模块负责人的结构，建议工作量约为 A 40%、B 30%、C 30%。主负责人承担跨平台适配和最终集成；B/C 的范围相对集中，仍各自对模块的交付质量负责。

| 角色 | 主责 | 交给其他人的内容 | 应与 AI 一起研究的问题 |
| --- | --- | --- | --- |
| A：主负责人 | Win32 扫描与控制、X11 后端、平台快捷键注册、共享接口和两平台集成。 | 接口能力表、最小可运行示例、失败情况、可演示版本和平台测试记录。 | 哪些顶层窗口可管理？句柄如何失效？权限/窗口管理器会限制哪些操作？Win32 和 X11 的语义如何对应？ |
| B：核心逻辑 | Workspace Manager、窗口筛选、切换规则、自动布局、配置保存；维护模拟后端和核心测试。 | 稳定的数据模型、状态变化规则和可供 UI 调用的命令。 | Workspace 是什么状态？窗口消失后如何清理？布局如何适配多显示器？哪些状态值得持久化？ |
| C：Qt 体验 | 总览 UI、Workspace 导航、窗口选择与反馈、Mac-like 视觉和交互。 | 使用模拟数据的可运行界面、交互说明与跨分辨率测试记录。 | Qt 事件循环和信号槽如何接入核心？如何更新实时窗口列表？缩略图不可用时如何降级？键盘操作如何设计？ |

接口或行为发生变化时，由提出变更的人先给出调用示例和失败场景，另外两人审阅后再修改共享接口。每人对自己的模块负责，同时至少复查一位组员的合并请求。

各阶段任务、交接产物和 AI 研究问题见 [三人分工执行说明](team-responsibilities.md)。

## 8. 开发阶段与验收节点

以下按约 16 周安排，可根据课程日历调整；每阶段先完成最小实验，再合入正式项目。

| 阶段 | 参考周次 | 阶段完成标志 |
| --- | --- | --- |
| 1. CMake + Qt + Git 骨架 | 1 | 三人能构建最小程序，约定分支、评审和编码方式。 |
| 2. Windows Window Scanner | 2–3 | 控制台程序能列出顶层窗口信息，并解释 Window、Process、HWND、`EnumWindows`。 |
| 3. Windows 窗口控制 | 4–5 | 最小示例能对普通窗口执行显示、隐藏、移动和缩放。 |
| 4. Workspace Manager | 6–7 | 模拟后端测试通过，能创建/切换 Workspace 并管理窗口归属。 |
| 5. Qt Mission Control UI | 8–10 | 可用鼠标和键盘完成总览、选择窗口和 Workspace 切换。 |
| 6. Linux X11 Backend | 11–12 | Linux X11 上跑通与 Windows 对应的核心演示流程。 |
| 7. 布局、快捷键、配置 | 13–14 | 预设布局、快捷键和重启恢复可演示。 |
| 8. 兼容性与完善 | 15–16 | 两平台构建、异常场景测试、演示脚本和课程报告完成。 |
| 9. 后续扩展 | 学期后 | 再评估 Wayland 等能力。 |

## 9. 共同验收场景

在 Windows 和 Linux X11 各运行一次：打开至少三个普通应用窗口；在总览中看到它们；创建两个 Workspace；把一个窗口移到另一个 Workspace；切换并找回该窗口；调整其位置和大小；尝试布局；关闭其中一个窗口并刷新；退出并重启后检查可恢复的设置。任何步骤失败，都应记录平台、桌面环境、窗口应用和实际行为。

课程答辩时，除演示结果，还应能讲清楚统一接口为什么存在、某个 Win32/X11 API 的输入输出与限制、核心逻辑如何在无桌面环境下测试，以及两平台行为不完全一致时如何处理。

## 10. 尚待团队确认的设计决定

1. **Workspace 语义**：第一版是否通过显示/隐藏窗口模拟工作区？这会影响窗口切换、任务栏行为和失败恢复。先做最小实验再定最终规则。
2. **窗口筛选规则**：哪些窗口出现在总览？需要在真实桌面样本上验证，不能只凭标题是否为空判断。
3. **多显示器与缩放**：第一版支持到什么程度？至少要保证单显示器正常，多显示器场景有明确行为。
4. **缩略图能力**：先验证两平台是否能稳定取到窗口图像，再决定是否纳入必交付内容。
5. **第三方代码使用**：DeskBox 可作为参考，但其实现语言、产品定位和许可证与本项目不同；任何代码复用都需先核对许可证、来源和课程要求。

## 11. 当前进度

仓库目前有最小 Qt 启动程序、Windows 控制台扫描器和初始的平台适配器接口。Mission Control UI、Workspace Manager、Linux X11、窗口控制、布局、快捷键、配置保存均未实现。构建方式见 [构建与启动](getting-started.md)，扫描器原理见 [Windows Window Scanner](windows-window-scanner.md)。本总览是团队协作与需求基线，完成一项功能后应同步更新其状态和验收结果。
