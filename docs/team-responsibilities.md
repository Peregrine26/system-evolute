# CrossDesk 三人分工执行说明

本文把 [项目总览](project-overview.md) 中的 A/B/C 三个角色拆成可认领的任务。A、B、C 是角色代号，填入姓名后即可用作小组任务表。时间按约 16 周估算；课程日历不同，可以移动周次，但保留阶段先后依赖。

本组采用 **一位主负责人 + 两位模块负责人** 的方式。建议工作量约为 A 40%、B 30%、C 30%；这是规划比例，实际以每周任务和课程要求调整。A 承担风险最高的跨平台 API、共享接口和最终集成；B 负责可独立测试的核心规则；C 负责可独立演示的 Qt 界面。B/C 的任务范围更集中，但各自仍负责完整的模块交付。

## 共同工作方式

- 每个阶段先写清楚一个真实问题，理解相关 API，完成最小可运行实验，记录构建与测试步骤，然后合入正式模块。实验可以先放在独立分支；不要把未验证的大段生成代码直接接入主程序。
- 每个任务有一名负责人、一名审阅人。负责人写代码、解释原理、提供复现方法；审阅人运行或检查验收步骤。共享接口变化须让受影响的两人参与讨论。
- 每周留出一次三人集成：在当周主力平台上构建，演示一条完整用户路径，记录失败窗口和下一周的阻塞项。Linux 阶段开始后，两平台都跑基础流程。
- 向 AI 提问时附上项目目标、当前接口、操作系统/桌面环境和实际观察；要求它解释 API 的前提、失败场景和最小实验。最终结论以实际运行结果和代码审查为准。

## A：主负责人，平台适配与集成

**责任边界**：所有直接调用 Win32 或 X11 的窗口操作由 A 主责。A 维护 `WindowApiAdapter` 的平台能力定义和后端实现，与 B 协商接口语义，并负责跨模块集成、两平台构建和最后的可演示版本。Qt UI 和 Workspace 代码不调用原生 API。A 应优先由对 C++、调试和构建系统最熟悉的组员担任。

现有起点是 `src/platform/window_api_adapter.h`、`src/platform/windows/win32_api_adapter.*` 和 `src/windows_window_scanner.*`。现有接口只覆盖查询，不能把后续控制能力当作已经存在。

| 阶段 | A 的具体任务 | 交付与验收 |
| --- | --- | --- |
| 2：Windows 扫描 | 理解 `HWND`、`EnumWindows`、标题、PID、进程名、窗口矩形；记录无标题/不可见/权限不足样本。 | 扫描器能输出真实窗口；关掉一个被扫描窗口后再次扫描不崩溃；附编译和运行命令。 |
| 3：Windows 控制 | 做显示/隐藏、移动、调整大小的最小实验；确认窗口无效、权限不足和目标应用拒绝操作时的结果。 | 一个可指定普通窗口的控制示例；接口返回可供 B/C 判断的成功或失败信息。 |
| 4–5：接口对接 | 与 B 定义查询快照、控制命令、失效窗口处理和错误表达；与 C 核对总览所需数据。 | 接口说明包含参数、返回值、失败语义和一个调用示例；模拟后端能实现同一接口。 |
| 6：X11 后端 | 在真实 X11 会话中逐项验证扫描和控制；记录与 Windows 不同的行为。 | Linux 上跑通与 Windows 对应的核心演示流程；列出未支持能力及回退方式。 |
| 7–8：平台收尾 | 负责系统级快捷键注册的底层部分；修复两平台差异和典型兼容问题。 | 快捷键占用时能返回失败；两平台构建与手工测试记录完整。 |
| 全程：集成主责 | 维护主程序构建、合并后的冒烟测试、跨模块问题清单和最终演示包；安排 B/C 参与联调。 | 每个阶段都有可运行版本；最终版本在 Windows 和 Linux X11 均能复现演示流程。 |

**A 和 AI 应研究并验证**：

1. `EnumWindows` 枚举的“顶层窗口”与任务栏窗口有何差别？实际会出现哪些不该管理的窗口？
2. `HWND` / X11 窗口标识在窗口关闭后还能否安全使用？调用前后怎样处理失效？
3. 读取标题、进程名、位置时，哪些字段可能缺失？缺失时怎样报告给上层？
4. Win32 的显示/隐藏、移动、调整大小与 X11 的对应操作，哪些只能发出请求，哪些能验证最终结果？
5. X11 的窗口列表、进程信息和桌面环境之间有哪些依赖？实际测试环境是什么？
6. 系统级快捷键冲突如何检测，用户如何知道快捷键没有生效？

**可直接用于 AI 的提问**：

> 我正在为 C++17/CMake 的 CrossDesk 编写 Win32 窗口控制适配器。当前接口见 `src/platform/window_api_adapter.h`。先解释 `HWND` 失效和窗口控制 API 的限制；再给一个只移动普通窗口的最小可运行示例、编译命令和失败场景。不要实现 Workspace 或 Qt UI。

## B：模块负责人，Workspace 与核心规则

**责任边界**：B 负责“窗口属于哪个 Workspace、切换后应该发生什么、如何布局和保存状态”。B 可以调用统一窗口接口，但核心模块不能包含 `windows.h`、X11 头文件，不能假定窗口标识永久有效。B 的主要任务可用模拟后端完成，不需要同时掌握 Win32 和 X11。

| 阶段 | B 的具体任务 | 交付与验收 |
| --- | --- | --- |
| 2–3：行为定义 | 用模拟窗口定义 Workspace 的创建、命名、删除、切换、窗口分配规则；与 A/C 决定第一版切换语义。 | 状态图或操作表；明确“删除有窗口的 Workspace”和“窗口消失”如何处理。 |
| 4：Workspace Manager | 实现平台无关的数据模型和命令；用模拟适配器测试核心流程。 | 能创建两个 Workspace、移动归属、切换并得到一致的状态；异常路径有测试。 |
| 5：UI 对接 | 给 C 提供当前 Workspace、各组窗口列表、可调用命令和操作结果；负责扫描结果与状态同步。 | C 使用模拟后端能完成总览和切换；外部窗口关闭后状态会更新。 |
| 7：布局和配置 | 计算窗口目标矩形；实现至少一种平铺策略；保存可长期存在的设置。 | 同样输入得到同样布局；屏幕可用区域内放置；重启恢复 Workspace 名称和设置。 |
| 8：核心测试 | 补充边界测试：空 Workspace、重复分配、窗口消失、删除 Workspace、配置损坏或旧版本。 | 自动化测试可在不打开真实桌面窗口的情况下运行。 |

**B 和 AI 应研究并验证**：

1. Workspace 是内存中的窗口分组，还是操作系统原生虚拟桌面？第一版切换后窗口如何显示/隐藏，失败时如何恢复？
2. 窗口扫描结果如何与当前分组同步？新增窗口默认进入哪里，关闭窗口后如何清理归属？
3. `native_handle` 只能代表当前会话中的窗口时，配置文件应该保存什么，不能保存什么？
4. 布局算法如何处理最小尺寸、屏幕可用区域、多显示器和用户自己移动窗口？
5. 核心操作的返回值需要表达哪些失败？怎样写模拟适配器覆盖这些场景？
6. 快捷键动作怎样映射到核心命令，而不让核心模块依赖某个平台的按键代码？

**可直接用于 AI 的提问**：

> 请帮我设计 CrossDesk 的 Workspace Manager 状态转换。约束：C++17；通过 `WindowApiAdapter` 操作窗口；核心不能包含 Win32/X11/Qt 类型；窗口可能随时关闭。先列出创建、删除、切换、移动窗口的规则和失败情况，再给最小内存模型与模拟适配器测试，不要生成完整项目。

## C：模块负责人，Qt 界面与用户体验

**责任边界**：C 负责用户看见和操作的部分，包括总览、Workspace 导航、窗口选择、操作反馈和视觉一致性。C 从 B 获取状态和命令，不直接调用 Win32/X11。Qt 选型和总览方案应先用小实验验证，再确定正式结构。C 先用假数据独立开发界面，再接入真实窗口数据。

| 阶段 | C 的具体任务 | 交付与验收 |
| --- | --- | --- |
| 1–3：Qt 基础 | 跑通最小 Qt 窗口；理解事件循环、信号槽和模型更新；用假数据画总览草图。 | 独立运行的小 UI，能显示多个 Workspace 和窗口条目。 |
| 4：交互原型 | 设计总览的打开/关闭、键盘焦点、窗口选择、窗口移动归属；先用模拟数据。 | 鼠标和键盘能完成关键动作；空列表和失败提示可见。 |
| 5：正式 UI | 接入 B 的核心接口；显示当前 Workspace、窗口列表和操作结果；处理刷新时窗口消失。 | 能在 Windows 上走通总览 -> 选择/移动窗口 -> 切换 Workspace 的完整流程。 |
| 6：Linux 适配验证 | 与 A 一起在 X11 桌面运行 UI，记录字体、窗口层级、缩放和焦点问题。 | 同一 Qt UI 在 Linux 上显示和交互正常；问题有复现步骤。 |
| 7–8：体验收尾 | 接入布局命令和快捷键反馈；完善高 DPI、不同分辨率、空状态、失败状态。 | 演示流程不依赖鼠标；缺少缩略图时仍能准确识别窗口。 |

**C 和 AI 应研究并验证**：

1. Qt 的事件循环、信号槽和模型/视图怎样把核心状态变化反映到界面？何时需要避免阻塞 UI 线程？
2. 总览如何在普通分辨率、高 DPI 和多显示器上排列窗口而不重叠？
3. 打开总览、选中窗口、切换 Workspace 时，键盘焦点和窗口焦点应该怎样变化？
4. 刷新列表后，已关闭窗口的条目如何消失，选择状态如何保持或清除？
5. 如果窗口图像抓取失败，界面如何用标题、进程名或图标提供可识别的回退？
6. 哪些视觉效果对于课程演示有价值，哪些会拖慢核心功能交付？

**可直接用于 AI 的提问**：

> 我需要给 CrossDesk 做 Qt 窗口总览原型。现在只有模拟的 Workspace/WindowInfo 数据。先解释 Qt 事件循环、信号槽和数据刷新；再给一个显示两个 Workspace、每个有几个窗口条目的最小可运行示例及 CMake 构建步骤。不要调用 Win32/X11，也不要实现完整 UI。

## 接口交接与审核

| 交接 | 提供方 | 接收方需要确认的事 |
| --- | --- | --- |
| 真实窗口能力 -> 核心 | A | B 确认返回的窗口数据、窗口失效和失败语义足够表达状态转换。 |
| 核心状态与命令 -> UI | B | C 确认能列出各 Workspace、发出操作并显示成功/失败。 |
| UI 需求 -> 平台能力 | C | A/B 确认需求可实现或有降级方案，特别是缩略图、焦点和快捷键。 |
| Linux 兼容结果 -> 全组 | A 主责，C 验 UI，B 验核心 | 记录 X11 会话类型、桌面环境、构建步骤和偏差；一起确定修复优先级。 |

一个任务完成时，请提交：代码或原型、运行截图/控制台结果、构建命令、至少一个正常路径和一个失败路径的测试记录、未解决问题。涉及共享接口时，PR 中写明调用方式变化；另一名组员复现后再合入。

## 工作量失衡时怎样调整

- A 的 X11 适配或两平台集成可能成为关键路径。B 可以接手模拟后端、配置和核心回归测试；C 可以接手 Linux UI 测试、构建文档和演示脚本，让 A 专注原生 API 问题。
- 如果 UI 进度落后，先保住可用的窗口列表、Workspace 切换和失败提示；动画、实时缩略图属于后续增强。
- 如果时间不足，三人先完成 P0 验收路径，再按项目总览的优先级加入自动布局、快捷键和配置。任何降级决定都由全组记录，避免有人继续依赖已推迟的功能。

## 前两周可以立即开始的任务

1. **全组**：在三台开发机确认 CMake、C++ 编译器、Qt、Git 和至少一个 Linux X11 测试环境；决定第一版 Workspace 切换的最小语义。
2. **A**：运行现有 Windows 扫描器，记录 5 类窗口样本和获取失败案例；提交问题清单。
3. **B**：写出 Workspace 操作表，用假窗口数据验证创建、切换、移动归属、关闭窗口的预期结果。
4. **C**：建立最小 Qt 原型，用假数据展示两个 Workspace；记录键盘/鼠标交互草图。

当前扫描器与接口还未经过这台环境的编译验证。正式分工开始后，第一位能在 Windows 开发环境构建的组员应记录真实构建结果，再把说明补进项目文档。
